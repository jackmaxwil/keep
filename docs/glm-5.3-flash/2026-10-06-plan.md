# GLM-5.3-Flash on one Mac: KEEP + RAMP plan

**Date:** 2026-10-06
**Decision owner:** Jack Mazac
**Status:** Draft. Phases 0 to 3 are done. Phase 5 onward waits on decisions
D1, D3 and D4 (section 10).

### Decision, 2026-10-06 (Jack): two Macs over Thunderbolt RDMA, no cloud

The campaign runs on this M4 Max plus the M5 Max, joined by JACCL over
Thunderbolt RDMA. No AWS. No download until Jack says so, and that includes
per-tensor range reads. What this changes:

- **Teacher and calibration** run pipeline-parallel: each Mac owns a
  contiguous layer range and holds only that range's tensors on its own disk,
  about 165 GB each. The 4-stream mHC hidden state (32 KiB per token) crosses
  the link once per chunk, about 32 MB per 1,024-token chunk. The pattern
  already exists in `benchmarks/export_glm45_air_distributed_teacher_cache.py`
  and the link preflight in `AGENTS.md` (direct ping, RDMA GIDs, UC pingpong,
  two-rank all-sum) must pass before any model work.
- **Quantization** splits by layer across both Macs. Each fits only the
  experts it already holds.
- **Runtime and every speed gate** run on the M5 Max, where NAX gives 16-bit
  E8P its fast kernels. The compressed model (about 90 GB) fits one Mac, so
  serving does not need the link. The non-NAX kernel gap on the M4 only
  matters if the M4 ever has to serve.
- **D2 is resolved** by this. D1 becomes a per-machine disk question.

## Goal

Run `zai-org/GLM-5.3-Flash` resident on one 128 GB Apple silicon Mac, text
only, with its 288 routed experts per layer compressed by KEEP and everything
else held near source precision. Prove quality against a captured teacher cache
with a paired uncompressed control, the same proof standard the
DeepSeek-V4-Flash headline uses.

Every number below cites the artifact that produced it. Numbers marked
**projection** are arithmetic on measured inputs, not measurements.

## 2. Architecture diff against DeepSeek-V4-Flash

Reference implementations used, pinned:

- transformers `v5.16.1`, `src/transformers/models/glm5_next/modeling_glm5_next.py`
  (the first tag that ships the module. The checkpoint was written by 5.16.0).
- SGLang commit `c19dc43cc732a3a7e9b487ba26f4af866cbe620b`,
  `python/sglang/srt/models/glm5_next.py` and `glm5_next_nextn.py`, for MTP,
  which transformers does not implement.

| Component | DeepSeek-V4-Flash | GLM-5.3-Flash | What RAMP has | Work |
| --- | --- | --- | --- | --- |

**Text path without the vision tower.** In the reference,
`Glm5NextTextModel.forward` builds `inputs_embeds` from `embed_tokens` and
never touches `model.visual` (lines 1441 to 1493). Image features are merged
only at image placeholder positions in `Glm5NextModel`. A text-only prompt has
none, so the text model alone is the complete computation. v1 classifies every
`model.visual.*` tensor as skip, never binds it, and a test asserts the binder
loads none of them.

**Where the decode bytes go (projection, from the census).** Every resident
tensor except the embedding is read once per decoded token: 13.96 GB at source
precision. The 8 active experts on 42 layers at 2.031 bpw add 2.15 GB, and the
KDA recurrent state is read and written once per layer, about 0.27 GB. So the
residents are **about 85 % of decode traffic**, and the 34 KDA layers alone
are 9.37 GB of BF16. This inverts the DeepSeek picture, where routed experts
dominated. Expert compression is what makes the model fit. Resident precision
is what sets decode speed. At the measured 409 GB/s the bandwidth ceiling is
about 25 tok/s with source-precision residents (16.4 GB per token), about
35 tok/s with 8-bit KDA and `kv_b_proj` (11.8 GB) and about 43 tok/s with
4-bit KDA projections (9.5 GB). These are ceilings, not predictions.

### Disk budget (projection)

| Item | Size | Basis |
| --- | ---: | --- |

| Calibration statistics | about 1 GB | 43 x 288 x 3 x 4096 floats, two variants |
| Working space | 20 GB | |
| **Total** | **about 450 GB** | |

Free today: 73 GiB (78 GB). **The routed artifact alone is 79 GB.** No design
finishes on this disk as it stands. Storage is needed whatever acquisition path
is chosen.

### Can it stream shard by shard?

- **Quantization: yes.** KEEP fits each expert projection independently given
  its importance vector. Peak working set is one decoded projection
  (`[2048,4096]` f32, 33.5 MB).
- **Importance statistics and the teacher cache: not shard by shard.** They
  need a forward pass through the whole model, in layer order. The shards are
  not layer ordered (census: all 43 MoE layers straddle two or three shards,
  interleaved with other layers' tensors). Hugging Face serves byte ranges,
  so the fix is to fetch tensors, not shards.
- **A layer-major fused pass** can avoid ever holding the checkpoint: fetch
  layer L's tensors by range (about 7.6 GB), run every session in the batch
  through layer L, accumulate layer L's importance, fit layer L's experts
  immediately, discard the FP8 bytes, move to L+1. The cost: hidden states for
  every token in the batch must persist between layers (4 mHC streams x 4096
  x bf16 = 32 KiB per token, so about 55 GB for the 40 calibration sessions at
  the teich pack's 42 K tokens per session), each extra teacher pass
  re-downloads 328 GB, and per-shard sha256 can only be checked when every byte
  of a shard has been fetched.

### Options

- **A. Recommended: one full copy on fast storage.** Either free about 450 GB
  internally or attach a 1 TB or larger NVMe over Thunderbolt. Download once
  with sha256 per shard, then reuse the proven per-session layer-major teacher
  design from DeepSeek (residents held, routed experts re-read per session from
  disk). This keeps every later pass (MTP targets, reruns, ablations) free.
- **B. No full copy.** The fused range-fetch pass above. Still needs about
  120 GB free for outputs, so it still needs space freed, and it costs one full
  download per teacher pass.
- **C. Partial.** Only for the cheap proofs below, which fetch single tensors
  by range and need under 10 GB in total. This is what Phases 1 to 4 use.

The download is over 100 GB, so it waits for Jack's yes (D1).

## 4. Calibration and the teacher cache

**Corpus.** The teich coding-agent pack (257 sessions, 10.8 M raw and 2.5 M
supervised tokens under the GLM-5.2 tokenizer, per the DeepSeek campaign plan).
The tokenizer is byte-identical, so its token ids carry over without
re-tokenization. The pack is not on this machine (D3). The GLM-5.3 chat
template differs from the one the pack was rendered with. v1 keeps the pack's
tokens as they are and records the template provenance in the manifest. If the
raw sessions are available, a re-render with the GLM-5.3 template is a cheap
follow-up.

**Splits.** Reuse the DeepSeek session-to-split assignment by `prompt_id` from
`recipes/dsv4_teich_split_manifest_v1_20260811.json`: calibration 40,
mtp-train 120, report 30, selection 30, holdout 37. Same sessions in the same
roles makes cross-family comparisons line up. A new manifest records GLM token
counts and per-split sha256, and a test asserts the splits are disjoint, as
`tests/test_dsv4_teich_manifest.py` does today. The holdout stays sealed until
the release-candidate gate.

**What "teacher" means.** FP8 weights dequantized exactly through
`keep.convert.fp8_block` (F32 scale multiply, then bf16 for the forward),
bf16 activations, the DSA indexer active, chunked prefill at a pinned chunk of
1024 tokens stamped into every artifact. This is weight-only FP8 (W8A16). The
served path quantizes activations to FP8 dynamically (W8A8). Matching that is
out of scope for v1 and listed as an open question.

**Memory, per session (projection).** Residents decoded to bf16, about 18 GB.
One MoE layer's experts as bf16, 14.5 GB, double-buffered so layer L+1 loads
behind layer L, 29 GB. Activations for a 42 K-token session at 32 KiB per
token, 1.4 GB. KDA state is fixed size (64 x 128 x 128 f32 per layer, 4 MiB).
DSA latent cache is 1 KiB per token per layer. Total about 50 GB, inside
128 GB with the wired limit left at its default.

**Outputs**, schema shared with the DeepSeek runner:

- Calibration: per (layer, expert, projection) column sums of squared
  activation, the router-weighted variant, and routed-token counts.
- Logits: top-2048 logits, `logsumexp` and `tail_mass` at supervised positions
  for report, selection and holdout.
- Later, mtp-targets for the drafter.

Throughput is unknown until measured. Phase 4 measures a single real layer's
prefill rate on this machine before any full run is scheduled.

## 5. The KEEP recipe

Nothing is inherited. The expert geometry is identical to DeepSeek-V4-Flash,
but three things changed that can move the answer: the source experts are FP8
(three mantissa bits) instead of FP4 (one), there are 288 experts at top-8
instead of 256 at top-6, and this machine has no NAX.

1. **Rate is pinned by memory, not by taste.** The full text model has to fit
   in about 92 GB to leave room for macOS, KV and activations. With about
   11 GB of residents, the routed budget, MTP experts included, is about
   81 GB. 2.031 bpw costs 79.1 GB (census `derived`), so there is little room
   above it. The search is for the best quality at or just above that rate.
2. **Re-derive codebook and group size.** A codeword covers 8 weights, so
   8-bit E8 codes cost about 1 bpw (1.03 at group 512, 1.5 at group 32) and
   16-bit E8P codes about 2 bpw (2.031 at group 512). At the rate the memory
   envelope allows, only E8P is in play. E8 stays in the ladder to place the
   curve. Sweep both on at least 16 experts stratified by routing frequency,
   from layers 3, 23 and 44. Measure importance-weighted relative error and
   block cosine, the same metrics as the DeepSeek pilot. Run once with uniform
   importance as soon as single experts can be fetched (Phase 3), and again
   with real importance after calibration (Phase 6).

   **First measurement, 2026-10-06, uniform importance.** Nine real experts
   (experts 0, 143 and 287 of layers 3, 23 and 44), fetched by byte range and
   decoded from FP8, through the whole ladder
   (`artifacts/quality/glm53-expert-vq-probe-uniform-20261006.jsonl`,
   `benchmarks/probe_glm53_expert_vq.py`):

   | Codebook | Group | bpw | Relative MSE per projection | Cosine per projection | Whole-expert cosine (synthetic inputs) |
   | --- | ---: | ---: | ---: | ---: | ---: |
   | E8 | 512 | 1.031 | 0.318 | 0.826 | 0.571 |
   | E8 | 32 | 1.500 | 0.308 | 0.832 | 0.584 |
   | E8P | 512 | 2.031 | 0.093 | 0.952 | 0.868 |
   | E8P | 256 | 2.062 | 0.092 | 0.953 | 0.869 |
   | E8P | 128 | 2.125 | 0.090 | 0.954 | 0.871 |
   | E8P | 32 | 2.500 | 0.084 | 0.957 | 0.881 |

   Same shape as DeepSeek: the codebook step dominates and group size is a
   weak rate dial (half a bit more buys a 10 % error cut). The three layers
   agree to three decimals. These rows use uniform importance and unit-variance
   synthetic inputs, so they rank configurations, they do not predict
   teacher agreement. Each E8P fit takes about 0.13 s per projection on this
   machine, which puts a full 36,288-projection pass near 80 minutes of fitting
   (projection).

3. **The kernel gap on this machine is real.** Every fast path in
   `vq_switch.py`, `switch_linear.py` and `gather_vqmm.py` gates on
   `code_bits == 8`, and the 16-bit E8P fast kernels are NAX-only. On this
   M4 Max a 2-bit artifact runs on the scalar path that cost DeepSeek its 8x.
   Either a simdgroup E8P gather kernel gets written for non-NAX GPUs or the
   runtime target moves to the M5 Max (D2). Phase 4 measures the scalar path
   on one real layer so the size of the gap is known before deciding.
4. **Importance.** Column activation energy per expert projection from
   calibration traffic, with the router-weighted variant (the AGQ affinity
   lever that won on GLM-4.5-Air) as a measured alternative, not a default.
5. **Uniform-importance fallback.** Any expert with fewer than 64 routed
   calibration tokens is fitted with uniform importance and named in the
   manifest. At about 1.7 M calibration tokens the average expert sees about
   47 K routed tokens (projection), so this should be rare. The count is
   reported, not assumed.
6. **Residents get their own study,** because they set decode speed. Candidates:
   MLX affine 8-bit on all KDA projections and `kv_b_proj`, then 4-bit on KDA
   q/k/v/o. Routers, `A_log`, `dt_bias`, conv weights, norms, mHC, the indexer
   and the embedding stay at source precision. Each candidate is measured
   against the teacher with experts held at source precision, so the resident
   cost is isolated before it is compounded with expert compression.
7. **MTP experts** are compressed at the backbone rate (1.8 GB) unless
   acceptance measurements say otherwise.
8. **Recovery sidecar, optional.** Only if the bare artifact misses the gate:
   the GLM-4.5-Air plan1 template, a rank-4 low-rank KD sidecar on the hardest
   late layer, picked by per-layer attribution and trained against teacher
   logits. It never mutates the seed artifact.

## 6. The RAMP adapter and kernels

**Files.** `src/ramp/models/glm5_next_policy.py` (headless: config
validation, layer schedule, tensor classification, source-name mapping),
`src/ramp/models/glm5_next_adapter.py` (MLX modules and binders),
`models/glm-5.3-flash.yaml` (profile), and a `glm5_next` `FamilyBinding` in
`ramp.models.registry`. Nothing gets edited into a shared module.

**Modules.**

- `Glm5NextKDA` on mlx-lm's vectorized gated delta kernel: GLM safe gate,
  `l2norm` q and k, separate q, k, v causal convs with SiLU, sigmoid-gated
  output RMSNorm. Decode (one token) and prefill both run the kernel, which is
  sequential over time inside each (head, value-dim) thread group. A chunked
  prefill kernel is an optimization to measure for, not to assume.
- `Glm5NextMLA`, NoPE, absorbed latent decode, plus `Glm5NextKPoolIndexer`.
- `Glm5NextMoE` with `QuantizedVQSwitchGLU`, bound by
  `bind_glm5_next_vq_experts`, and dense MLP layers 0 to 2.
- mHC reused from the DSV4 adapter, mean-collapse head.
- Cache per layer: KDA conv and recurrent state, DSA latent KV plus the
  indexer's packed key and gate cache.

**Parity tests.** A fixture script runs the pinned transformers v5.16.1
reference in an isolated `uv run --with torch` environment (torch never
becomes a project dependency) on tiny random configs, and commits small
`.npz` fixtures. Tests compare the MLX modules against them in fp32 at
1e-5 relative error:

1. A KDA layer, both reference paths (chunked prefill and one-token recurrent
   decode), including state carried across calls.
2. MLA plus the k-pool indexer, short context (dense equivalence) and long
   context (sparse selection with tail).
3. One KDA decoder layer and one DSA MoE decoder layer with mHC.
4. A tiny full model end to end.

bf16 drift against the fp32 reference is measured and recorded, not asserted
to zero.

**Indexer tie order (decided 2026-10-06).** The indexer's ReLU makes
exact-zero pool scores common, and the first fixture had ties at the top-k
cut on 3 of 46 positions. torch on CPU picked pool sets that neither a
lowest-index nor a highest-index rule reproduces, and CUDA serving kernels
will order ties their own way, so tie order is implementation-defined, not
part of the model. RAMP breaks ties by lowest pool index, deterministically,
and the teacher and the compressed model share that code, so the teacher
cache stays self-consistent. The fixture generator rejects any seed with a
tie at a cut (it uses 8 indexer heads, and its check rejects the earlier
2-head config), so the parity tests test the architecture, not tie order. Real-weight parity on layer 0 (KDA plus dense MLP, about 540 MB by
range fetch) follows in Phase 3.

**Kernel dispatch for these shapes.** Same K and N as DeepSeek, eight routes
per token instead of six, 288 experts. Measure on this machine, at M=1
(decode), M of 2 to 8 (MTP verify) and sorted prefill, every gather VQ
variant that runs without NAX. Pin the decision table with tests. Make a
missing fast path loud, as the DeepSeek handoff demanded.

**MTP drafting (v1.1).** Port the NextN block. The hard part is speculative
verify with KDA: a recurrent state cannot be trimmed after a rejected draft,
so verify must keep per-position states for the drafted window (about 4 MiB
per KDA layer per position, so about 544 MiB for four positions across 34
layers, projection) or re-run the accepted prefix. Acceptance rate is the
first number that catches a transcription error, so a surprisingly good one is
treated as a suspect result.

## 7. Evaluation and what "done" means

Written before any model work, so the targets cannot drift toward the results.

| Gate | Target | How measured |
| --- | --- | --- |
| Size | text-only runnable model at most 92 GB on disk | manifest byte totals, all files sha256-verified |
| Memory | high-water at most 110 GB through a 32 K-token prefill plus 512 decoded tokens, zero swap and zero pageouts | `resource` peak plus `vm_stat` deltas, fresh process |
| Audit | zero dense routed experts, zero unbound VQ experts, fallback experts named | artifact audit |
| Quality, report split (30 sessions) | mean KL at most 0.30 with both ends of the tail-corrected bracket passing, top-1 at least 0.85, top-5 and top-10 reported | `eval_*_teacher_cache.py run` |
| Control | uncompressed model on the **same 30 sessions**: KL at most 1e-6, top-1 at least 0.999 | `control` verb. The DeepSeek control only ran on 8 sessions. This one runs on all 30 so the perplexity cost is known for the whole split |
| Decode | at least 20 tok/s at M=1, 4 K context, greedy, on the target machine | quiet-window rows, fresh process, ratios with controls |
| Prefill | at least 3x the streamed FP8 source engine on a 4 K prompt | same harness, same prompts |
| Holdout | touched once, at the release-candidate gate | sealed until then |

The uncompressed reference engine cannot hold the 328 GB source, so it runs
layer-streamed from disk. That makes it a fair prefill baseline (weights are
read once per layer per prompt) and an unusable decode baseline (it would
re-read about 305 GB of experts per token). For decode, the same-machine
control is an MLX affine artifact of the same model at equal or larger size,
which also answers whether lattice VQ beats affine at equal bytes on this
family. Speculative MTP is not a v1 gate.

## 8. Risks, open questions, and phase order

### Risks

1. **No NAX on this machine.** The target rate needs 16-bit E8P, and the fast
   kernels that made DeepSeek viable do not run here. Mitigation in section 5,
   step 3.
2. **KDA prefill speed.** The available kernel is time-sequential. Long-prompt
   prefill may be KDA-bound. Measured in Phase 4.
3. **FP8 to 2 bits is a bigger step than FP4 to 2 bits.** The DeepSeek source
   was already 4-bit. Expect worse fit error at the same rate, and budget for
   the recovery sidecar.
4. **MTP seam.** No transformers reference, no `hc_*` tensors on layer 45.
   Mitigated by treating MTP as v1.1 with its own reference capture.
5. **Teacher definition.** W8A16 rather than the served W8A8. The reported
   agreement is against the dequantized model.
